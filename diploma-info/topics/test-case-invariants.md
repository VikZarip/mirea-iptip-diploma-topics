# Разработка веб-сервиса для генерации автотестов на основе инвариантов, извлечённых из ручных тест-кейсов с помощью LLM

**Статус:** Зарезервирована

**Уровень:** бакалавриат

## Краткое описание

В проектах накапливаются сотни и тысячи ручных тест-кейсов, а автоматизированы из них немногие. В тест-кейсах при этом уже записаны правила системы — бизнес-правила («в архивный канал нельзя писать», «архивировать команду может только администратор») и правила интерфейса («деструктивные действия выделены как деструктивные»). Каждое такое правило — инвариант: оно должно выполняться всегда, а не только в одном примере.

Тема посвящена веб-сервису, который с помощью LLM выделяет из ручных тест-кейсов кандидаты в инварианты, даёт QA-инженеру подтвердить или поправить их и по подтверждённым инвариантам генерирует автотесты для системы.

## Направление работы — выбрать одно

| | **А. UI/UX-слой: логика интерфейса через эвристики** | **Б. Бизнес-слой: устойчивые паттерны** |
|---|---|---|
| Что извлекается | Правила интерфейса, сгруппированные по эвристикам юзабилити (Нильсен): видимость состояния системы, предотвращение ошибок, согласованность, понятные сообщения об ошибках | Бизнес-правила по паттернам тест-дизайна: переходы состояний, предусловия действий, доступ по ролям, ограничения значений, лимиты |
| Пример инварианта | «Любое деструктивное действие оформлено как деструктивное и требует подтверждения» | «В архивном канале нельзя публиковать сообщения, менять участников и настройки» |
| Какие кейсы | UI-кейсы: меню, диалоги, состояния экранов, сообщения | Кейсы с явными правилами: статусы, права, лимиты, негативные проверки |
| Чем проверяется | UI-автотесты (Playwright): одно правило проверяется для **всех** элементов интерфейса данного вида | API-автотесты (pytest + Hypothesis): property-based и stateful-тесты через REST API |
| Основная метрика | Доля UI-кейсов, сведённых к правилам; нарушения правил, найденные в реальном интерфейсе | Mutation score сгенерированных тестов на серверной части |
| Главный риск | Эвристики сформулированы широко — правило должно быть проверяемым («выделено красным и требует подтверждения»), а не оценочным («удобно») | В наборе мало кейсов на одно правило — правило остаётся гипотезой |

Направление выбирается на этапе анализа, после знакомства с тест-кейсами выбранных функциональных областей. Совмещать оба направления в бакалаврской ВКР не нужно.

## Ожидаемый результат

- Веб-сервис: загрузка ручных тест-кейсов, извлечение кандидатов в инварианты, экран проверки инвариантов QA-инженером, генерация автотестов.
- Формат описания инварианта: множество объектов, условие, тип правила, ссылки на тест-кейсы-источники.
- Сгенерированные автотесты для системы-мишени, запускаемые в CI.
- Отчёт о проверке на открытом наборе тест-кейсов: метрики «до/после».
- Пояснительная записка, руководство пользователя, презентация.

## Возможные функции/компоненты

- **Импорт тест-кейсов**: Markdown/CSV/экспорт из системы управления тестированием.
- **Очистка от чувствительных данных до передачи LLM**: токены и ключи доступа, пароли, e-mail, IP-адреса и внутренние хосты, ссылки на внутренние трекеры, ФИО и данные клиентов заменяются метками (`<TOKEN_1>`, `<EMAIL_2>`, `<HOST_1>`). Одинаковые значения получают одинаковую метку, чтобы связи между кейсами не терялись. Обратная подстановка — только локально, при генерации тестов. Журнал замен хранится вместе с результатами.
- **Извлечение инвариантов**: LLM разбирает тест-кейсы в структуру и предлагает правила; у каждого правила — ссылки на кейсы-основания.
- **Проверка человеком**: принять, исправить, отклонить; правило из одного кейса помечается как гипотеза.
- **Поиск противоречий** между тест-кейсами (один кейс разрешает переход, другой запрещает).
- **Генерация автотестов** по подтверждённым инвариантам для 2–3 типов правил выбранного направления.
- **Запуск и отчёт**: какие инварианты нарушены в системе-мишени.
- *Опционально*: экспорт инвариантов как чек-листа для ручного регресса.

## Технологические ожидания

- Backend: Python (FastAPI); LLM — открытая модель (например, Qwen) локально или через API.
- Автотесты: направление А — [Playwright](https://playwright.dev/); направление Б — pytest + [Hypothesis](https://hypothesis.readthedocs.io/) для property-based и stateful-тестов, клиент к REST API системы-мишени.
- Frontend: React/Vue.
- БД: PostgreSQL или SQLite.
- Система-мишень: Mattermost в Docker ([mattermost-preview](https://hub.docker.com/r/mattermost/mattermost-preview)), [REST API](https://api.mattermost.com/).

## Метрики успеха

- Основная метрика выбранного направления (см. «Направление работы»).
- Ни одного чувствительного значения в запросах к LLM: журнал запросов проверяется сканером секретов и персональных данных.
- Доля предложенных инвариантов, принятых QA-инженером без правок.
- Время от ручного тест-кейса до работающего автотеста: вручную и с сервисом.
- Устойчивость извлечения: доля совпадающих инвариантов при повторных запусках на одних и тех же кейсах.
- Сравнение с существующими автотестами проекта: какие правила из тест-кейсов покрыты там и какие — сгенерированными тестами.

## Основные use cases

- **QA-инженер** загружает набор ручных тест-кейсов модуля и получает список кандидатов в инварианты с основаниями.
- **QA-инженер** подтверждает, правит или отклоняет инварианты; видит противоречия между тест-кейсами.
- **QA-инженер** генерирует автотесты по подтверждённым инвариантам и запускает их на тестовом стенде.
- **Тимлид QA** видит, какие правила системы покрыты автотестами, а какие проверяются только вручную.

## Актуальность

- Автоматизация ручных тест-кейсов — дорогая и медленная работа; генерация тестов по одному кейсу даёт хрупкие сценарные тесты, а правило, выведенное из группы кейсов, проверяется устойчивее.
- Существующие генераторы (например, [Schemathesis](https://schemathesis.readthedocs.io/) по спецификации OpenAPI) проверяют схему API, но не бизнес-правила.
- Для бакалаврской ВКР научная новизна не требуется: акцент на проектировании и реализации работающего сервиса.

## Методы, модели и данные

- Направление А: эвристическая оценка интерфейса (10 эвристик Нильсена) как каталог типов UI-правил.
- Направление Б: техники тест-дизайна как источник правил — граничные значения, классы эквивалентности, переходы состояний, таблицы решений.
- LLM со структурированным ответом (JSON-схема) для разбора тест-кейсов; человек подтверждает результат.
- Очистка данных: поиск секретов ([detect-secrets](https://github.com/Yelp/detect-secrets), [gitleaks](https://github.com/gitleaks/gitleaks)), поиск персональных данных ([Presidio](https://microsoft.github.io/presidio/); для русского текста — [Natasha](https://github.com/natasha/natasha)), регулярные выражения для хостов, IP и ссылок. Правила обработки персональных данных — [240-ethics-data.md](../guides/240-ethics-data.md).
- Property-based и stateful-тестирование, мутационное тестирование для оценки сгенерированных тестов.
- Данные — см. «Источники данных».

## Практическая польза

- Бизнес-правила, разбросанные по сотням ручных тест-кейсов, становятся явным проверяемым списком.
- Часть ручного регресса заменяется автотестами без написания каждого теста вручную.
- Противоречия в тест-кейсах находятся до того, как приведут к пропущенному дефекту.

### Этапы проекта (план студента)

1. Изучение тест-кейсов Mattermost, выбор 1–2 функциональных областей и **направления работы (А или Б)**; обзор аналогов.
2. Формат инварианта и каталог поддерживаемых типов правил для выбранного направления.
3. Проектирование архитектуры, модели данных и интерфейса проверки.
4. Извлечение инвариантов, экран проверки, поиск противоречий.
5. Генерация и запуск автотестов на Mattermost в Docker.
6. Замеры «до/после» по метрикам выбранного направления, оформление ВКР.

### Источники данных

- **Ручные тест-кейсы Mattermost** — [github.com/mattermost/mattermost-test-management](https://github.com/mattermost/mattermost-test-management), лицензия Apache 2.0. Около 5 тыс. кейсов в Markdown (шаги, ожидаемый результат, метаданные), разложенных по функциональным областям. Для направления Б удобна область архивирования каналов и команд (~80 кейсов: запреты действий в архивном канале, права, восстановление, лимиты); для направления А подходят кейсы меню, диалогов и состояний каналов.
- **Эталон для сравнения**: около 1 тыс. кейсов уже автоматизированы командой Mattermost (поле `cypress: in Production` в метаданных кейса); тесты — в [e2e-tests основного репозитория](https://github.com/mattermost/mattermost/tree/master/e2e-tests/cypress).
- **Система-мишень**: открытый Mattermost в Docker, REST API — [api.mattermost.com](https://api.mattermost.com/).
- **Чувствительные данные встречаются даже в открытом наборе**: токены доступа (в том числе JWT) — в 4 кейсах, внутренние тестовые хосты — в 142, ссылки на внутренний Jira — более чем в 1000. В рабочих тест-кейсах к ним добавятся данные клиентов и сотрудников — их нельзя передавать во внешний API без очистки (152-ФЗ, NDA).
