# Разработка веб-приложения для управления требованиями программного проекта с трассировкой и поиском дублирующихся требований

**Статус:** Свободно

**Рекомендуемый уровень:** бакалавриат

## Краткое описание

В крупных ИТ-проектах требования хранятся в разрозненных документах и таск-трекерах, быстро устаревают, дублируют и противоречат друг другу, а связь «требование → задача → тест» теряется. Тема посвящена разработке веб-приложения, в котором требования ведутся централизованно, связываются между собой и с артефактами проекта (матрица трассировки), а похожие и дублирующиеся требования находятся автоматически.

## Ожидаемый результат

- Веб-приложение для ведения требований проекта с версионированием и статусами.
- Матрица трассировки «требование ↔ требование ↔ задача ↔ тест».
- Модуль поиска похожих и дублирующихся требований с подсветкой пар-кандидатов.
- Импорт и экспорт требований (CSV/Excel/Markdown).
- Пояснительная записка, руководство пользователя, презентация.

## Возможные функции/компоненты

- **Реестр требований**: создание, редактирование, атрибуты (тип, приоритет, источник, статус), история изменений.
- **Трассировка**: связи между требованиями и с внешними артефактами (задачи, тест-кейсы), визуализация матрицы и графа связей.
- **Поиск дубликатов**: сравнение формулировок (TF-IDF / векторные представления предложений), порог сходства, ручное подтверждение или отклонение.
- **Импорт/экспорт**: CSV, Excel, Markdown; опционально — импорт задач из Jira/GitHub Issues.
- *Опционально*: проверка качества формулировок (неоднозначные слова «быстро», «удобно», «и т.п.»), отчёт о покрытии требований тестами.

## Технологические ожидания

- Backend: Python (FastAPI/Django) или Node.js/TypeScript.
- Frontend: React/Vue.
- БД: PostgreSQL; для поиска похожих — scikit-learn или sentence-transformers.
- Развёртывание: Docker Compose.

## Метрики успеха

- Ведение не менее 200 требований без заметной деградации интерфейса.
- Точность поиска дубликатов на размеченном наборе — не ниже 70% (precision@10).
- Построение матрицы трассировки для всего проекта одним действием.

## Основные use cases

- **Аналитик** заводит требования, связывает их между собой и с задачами, видит непокрытые требования.
- **Аналитик** запускает поиск дубликатов, просматривает пары-кандидаты и объединяет повторы.
- **Руководитель проекта** выгружает матрицу трассировки для отчёта заказчику.
- **Тестировщик** видит, какие требования не покрыты тест-кейсами.

## Актуальность

- Ошибки в требованиях — одна из главных причин переделок в ИТ-проектах; коммерческие системы управления требованиями дороги и избыточны для небольших команд.
- Для бакалаврской ВКР научная новизна не требуется: акцент на проектировании и реализации работающего прототипа.

## Методы, модели и данные

- Метрики текстового сходства: косинусное сходство TF-IDF, эмбеддинги предложений (например, модели семейства SBERT для русского языка).
- Данные: открытые наборы требований (PROMISE NFR, PURE), учебные ТЗ.

## Практическая польза

- Аналитики тратят меньше времени на поиск повторов и сверку требований; руководитель проекта видит покрытие требований задачами и тестами.

### Этапы проекта (план студента)

1. Обзор процессов управления требованиями и аналогов (Jira + Confluence, ReqView, Doorstop и др.).
2. Формулирование требований к приложению, модель данных требований и связей.
3. Проектирование архитектуры и интерфейсов.
4. Реализация реестра требований и трассировки.
5. Реализация поиска дубликатов, подготовка тестового набора.
6. Тестирование, оценка точности поиска, оформление ВКР.

### Источники данных

- PROMISE NFR dataset, PURE (Public Requirements dataset).
- Учебные технические задания и требования курсовых проектов.
