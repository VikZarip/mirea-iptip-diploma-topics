# Разработка веб-приложения для учёта и визуализации технического долга программного проекта с интеграцией с Git

**Статус:** Свободно

**Рекомендуемый уровень:** бакалавриат

## Краткое описание

Технический долг накапливается незаметно: о нём знают разработчики, но его не видно в планировании. Тема посвящена разработке веб-приложения, которое собирает метрики из истории Git-репозитория и статического анализа кода, позволяет вручную регистрировать и приоритизировать элементы технического долга и показывает «горячие точки» проекта, где рефакторинг принесёт наибольшую пользу.

## Ожидаемый результат

- Веб-приложение, подключаемое к Git-репозиторию (GitHub/GitLab или локальный).
- Автоматический сбор метрик по файлам и модулям.
- Реестр элементов технического долга с оценкой и приоритетом.
- Дашборд: карта «горячих точек», динамика долга во времени.
- Пояснительная записка, руководство пользователя, презентация.

## Возможные функции/компоненты

- **Интеграция с Git**: частота изменений файлов (churn), авторы, совместные изменения файлов.
- **Метрики кода**: цикломатическая сложность, размер, дублирование, маркеры TODO/FIXME/HACK.
- **Горячие точки**: сочетание сложности и частоты изменений (подход «code as a crime scene»).
- **Реестр долга**: ручное добавление записей, тип (архитектурный, кодовый, тестовый, документационный), оценка трудозатрат и влияния, приоритет.
- **Визуализация**: treemap/heatmap по структуре проекта, графики динамики.
- *Опционально*: создание задач в GitHub Issues/Jira из реестра, импорт результатов SonarQube.

## Технологические ожидания

- Backend: Python (FastAPI) + GitPython/PyDriller, radon/lizard для метрик; или Node.js.
- Frontend: React/Vue + D3/ECharts.
- БД: PostgreSQL или SQLite.
- Развёртывание: Docker.

## Метрики успеха

- Анализ репозитория с историей 1000+ коммитов — не дольше нескольких минут.
- Поддержка метрик минимум для одного языка программирования (Python или Java/TypeScript).
- «Горячие точки», найденные приложением, совпадают с мнением разработчиков проекта для большинства топ-10 файлов.

## Основные use cases

- **Тимлид** подключает репозиторий и видит, какие модули чаще всего меняются и сложнее всего устроены.
- **Разработчик** регистрирует найденный долг с оценкой и ссылкой на файл.
- **Менеджер** при планировании спринта выбирает элементы долга по приоритету.

## Актуальность

- Технический долг напрямую влияет на скорость разработки; существующие инструменты (SonarQube, CodeScene) либо не учитывают историю изменений, либо платные.
- Для бакалаврской ВКР научная новизна не требуется: акцент на проектировании и реализации работающего приложения.

## Методы, модели и данные

- Анализ истории версий (mining software repositories), метрики сложности кода.
- Модели приоритизации: матрица «влияние × трудозатраты», взвешенная оценка.
- Данные: открытые репозитории на GitHub.

## Практическая польза

- Технический долг становится видимым и планируемым; команда тратит время на рефакторинг там, где это действительно окупается.

### Этапы проекта (план студента)

1. Изучение понятия технического долга, метрик и аналогов (SonarQube, CodeScene, Code Climate).
2. Выбор набора метрик и модели приоритизации.
3. Проектирование архитектуры, модели данных и интерфейсов.
4. Реализация сбора метрик из Git и кода.
5. Реализация реестра долга и дашборда.
6. Проверка на открытых репозиториях, оформление ВКР.

### Источники данных

- Открытые репозитории GitHub (например, проекты Apache, Django, FastAPI).
- Книга A. Tornhill «Your Code as a Crime Scene» — подход к поиску горячих точек.
